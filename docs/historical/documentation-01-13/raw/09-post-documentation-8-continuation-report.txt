## 2. Executive Delta Summary

### 2.1
The platform underwent five major structural progressions after Documentation 8:
1. Movement module gained scheduling, dispatch lifecycle, connected-movement protocol, and external-location support.
2. Boarding admissions became a first-class domain with dedicated tables, RLS, permission definitions, status history, and care notes.
3. Breeding domain expanded with foalings entity, breeding contracts, source-mode tracking (internal/connected/external), and semen-batch quality fields.
4. Financial infrastructure matured with supplier payables, invoice status expansion, and a reusable `FinancialStatusSection` traceability component deployed across Vet and Breeding detail sheets.
5. The Identity/Profile layer was built from scratch: signup fixes, personal profile editing page, personal-vs-organization routing separation, public profile full localization, and bilingual organization identity groundwork.

### 2.2
Most important completed workstreams: (a) Identity/profile architecture — from non-existent personal profile to a fully separated personal/organization identity model; (b) Financial traceability — reusable component showing invoice, stable cost, and payable status inline on any source entity; (c) Boarding admissions as an operational domain.

### 2.3
Biggest structural shift: The platform went from having one blurred "profile" concept (organization public profile only) to a strict dual-identity model where personal profile (`/dashboard/my-profile`, `profiles` table) and organization profile (`/dashboard/public-profile`, `tenants` table) are architecturally separated with mode-aware routing guards and distinct CTAs.

### 2.4
Intentionally deferred: phone-only authentication, multi-value contact support, full public-profile layout redesign beyond the sticky-save and column-redistribution improvements already applied, personal display-name vs legal-name separation.

### 4.1
Major workstreams:

### 4.2

#### 4.2.1–4.2.4 W1: Movement Lifecycle
- **Initial:** Movements were immediate-only, internal-only.
- **Audit outcome:** Required scheduling, dispatch lifecycle, external locations, connected tenant movements.
- **Execution:** Added `movement_status`, `scheduled_at`, `dispatched_at`, `completed_at` to `horse_movements`. Created `external_locations` table. Added notification triggers for boarding, movement, and incoming events.
- **Final state:** Movements support scheduled→dispatched→completed lifecycle. External locations are first-class. Connected movements create incoming records at dispatch time, not scheduling time.

#### 4.2.1–4.2.4 W2: Boarding Admissions
- **Initial:** No boarding admissions entity existed.
- **Execution:** Created `boarding_admissions`, `boarding_status_history`, `horse_care_notes` tables with full permission-based RLS policies.
- **Final state:** Complete operational domain with admission, checkout, status tracking, and care notes.

#### 4.2.1–4.2.4 W3: Breeding Expansion
- **Initial:** Breeding had attempts, pregnancy checks, embryo transfers but no foalings, contracts, or provider-source tracking.
- **Execution:** Created `foalings` table (with registry/lifecycle tracking), `breeding_contracts` table (with pricing, client, service linkage). Added `source_mode`/`provider_tenant_id`/`external_provider_name`/`performed_by` to breeding_attempts and embryo_transfers. Extended semen_batches with source tracking and quality fields. Added `stallion_id` to pregnancies. Updated breeding_role constraint.
- **Final state:** Breeding domain has full lifecycle coverage from attempt through pregnancy to foaling, with contract management and provider-source tracking.

#### 4.2.1–4.2.4 W4: Financial Traceability
- **Initial:** No supplier payables. No reusable traceability component. Invoice status values were limited.
- **Execution:** Created `supplier_payables` table. Expanded invoice status constraint to include `reviewed`, `approved`, `shared`, `issued`, `sent`. Created `FinancialStatusSection` component showing invoice/cost/payable status inline. Created `InternalCostsTab` and `SupplierPayablesTab` in finance module. Created `useSupplierPayableForSource` hook. Deployed `FinancialStatusSection` to Vet `TreatmentDetailSheet`, Breeding `BreedingDetailSheets`, and `FoalingDetailSheet`.
- **Final state:** Any source entity (treatment, breeding attempt, foaling) can display its financial traceability inline with clickable invoice drill-through.

#### 4.2.1–4.2.4 W5: Housing Refinements
- **Initial:** Post-Phase 1 gaps: no capacity column on facility_areas, no housing-sync triggers, no server-side capacity enforcement.
- **Execution:** Added `capacity` column. Created `sync_horse_housing_unit_id` trigger for denormalized field consistency. Created `enforce_unit_capacity` trigger for server-side validation (single-occupancy and max-capacity checks). Added `storage` and `isolation_room` to `internal_unit_type` enum.
- **Final state:** Housing integrity is enforced at the database level, not only in application code.

#### 4.2.1–4.2.4 W6: Identity/Profile Architecture

- **Final state:** Complete dual-identity model with personal profile page, mode-aware routing, fully localized public profile, bilingual org identity fields, sticky save bars, and personal-mode UX corrections.

## 9. Identity / Signup / Personal Profile / Organization Profile Delta

### 9.1
This was the most substantial architectural workstream in this delta period, progressing through a formal audit, four execution stages, and two follow-up correction passes.

### 9.2

#### 9.2.1 Signup Language Switcher
`LanguageSelector` component was added to the `Auth.tsx` header area (Row 1 of mobile header). Users can now switch language before starting signup/signin.

#### 9.2.2 Signup Phone Persistence Fixes
Two-stage fix:
1. `AuthContext.signUp()` was updated to pass `phone` in `data` metadata: `data: { full_name: fullName, phone: phone || undefined }`.
2. The `handle_new_user` database trigger was replaced (migration `20260328051924`) to extract phone from metadata: `NEW.raw_user_meta_data ->> 'phone'` and insert into `profiles.phone`.

This ensures end-to-end persistence: signup → auth metadata → trigger → `profiles.phone`.

#### 9.2.3 Personal Profile Page Creation
`DashboardMyProfile.tsx` was created as a dedicated personal profile editing page at route `/dashboard/my-profile`. It uses:
- `useAuth()` for profile data
- `useUpdateProfile()` hook for persistence
- Fields: `full_name` (English), `full_name_ar` (Arabic), `phone`, `bio`, `location`, `website`
- `BilingualName` component for header display
- Sticky save bar when form is dirty
- `BackButton` for desktop navigation back to dashboard
- Full i18n coverage via `myProfile.*` keys

#### 9.2.4 Personal vs Organization Routing Correction
- `/dashboard/my-profile` wrapped in `<WorkspaceRouteGuard requiredMode="personal">` in `App.tsx` — inaccessible in organization mode.
- `/dashboard/public-profile` wrapped in `<WorkspaceRouteGuard requiredMode="organization">` — inaccessible in personal mode.
- `myProfile` added to `NAV_MODULES` in `navConfig.ts` with `visibleIn: "personal"`.

#### 9.2.5 Personal Mode UX Corrections
Dashboard.tsx was updated across three execution passes:
- Organization-specific elements (horse lists, upcoming events, add-horse dialog, tenant/role switchers) are hidden when `workspaceMode === "personal"`.
- Personal quick actions grid shows: My Profile, Community, My Bookings, My Payments, Favorites (coming soon).

#### 9.2.6 CTA Wording/Destination Corrections
- Personal mode: Gold-styled "Complete Your Personal Profile" (أكمل ملفك الشخصي) CTA → `/dashboard/my-profile`. Condition: `workspaceMode === "personal" && !profile.bio && !profile.location`.
- Organization mode: Orange-styled "Complete Your Public Profile" (أكمل ملفك العام) CTA → `/dashboard/public-profile`. Condition: `workspaceMode === "organization" && activeRole === 'owner' && !activeTenant.tenant.slug`.

#### 9.2.9 Public Profile Layout Redistribution

`CreateStableProfile.tsx` updated with `name_ar` and `description_ar` fields in `formData`, providing bilingual name and description input in the organization creation wizard.

## 10. Regression and Corrective-Pass History

### 10.1–10.2

#### 10.2.1–10.2.5 Regression 1: Phone Data Loss
- **What broke:** Phone entered at signup was silently discarded.
- **Cause:** `Auth.tsx` captured phone in `formData.phone` but `signUp()` in `AuthContext.tsx` did not accept or pass a phone parameter.
- **Diagnosis:** Audit identified that `signUp()` only accepted `email`, `password`, `fullName`.
- **Fix (Stage 1):** Added `phone` parameter to `signUp()` and passed it in `options.data` metadata.
- **Fix (Stage 2):** Updated `handle_new_user` trigger to extract `NEW.raw_user_meta_data ->> 'phone'` and insert into `profiles.phone`.
- **Fully closed:** Yes. End-to-end: signup form → auth metadata → trigger → `profiles.phone`.

#### 10.2.1–10.2.5 Regression 2: My Profile Invisible in Personal Mode
- **What broke:** After creating `DashboardMyProfile.tsx` and adding it to routes, the page existed but was not discoverable in the actual personal-mode UX.
- **Cause:** Initial implementation relied only on sidebar navigation entry, which was insufficient for mobile and for users unfamiliar with navigation structure.
- **Diagnosis:** Follow-up pass identified that "route existence ≠ UX discoverability."
- **Fix:** Added `myProfile` to `NAV_MODULES` with `visibleIn: "personal"` (making it appear in sidebar and `MobileHomeGrid`). Added My Profile as first card in personal-mode quick actions grid on Dashboard.
- **Fully closed:** Yes.

#### 10.2.1–10.2.5 Regression 3: Organization Content Leaking into Personal Mode
- **What broke:** Horse lists, upcoming events, add-horse dialog, and tenant/role switchers appeared in personal mode dashboard.
- **Cause:** Dashboard.tsx had no `workspaceMode` gating on these organization-specific elements.
- **Diagnosis:** Follow-up execution pass identified the semantic contamination.
- **Fix:** Wrapped organization-specific sections in `workspaceMode === "organization"` conditionals.
- **Fully closed:** Yes.

#### 10.2.1–10.2.5 Regression 4: Personal-Mode CTA Routing to Org Profile
- **What broke:** "Complete Your Public Profile" CTA appeared in personal mode, routing to organization profile.
- **Cause:** CTA condition did not check `workspaceMode`.
- **Fix:** Added `workspaceMode === "organization"` guard to org CTA. Created separate personal CTA with `workspaceMode === "personal"` condition routing to `/dashboard/my-profile`.
- **Fully closed:** Yes.

#### 10.2.1–10.2.5 Regression 5: No Desktop Back Button on My Profile
- **What broke:** `MobilePageHeader` is `lg:hidden`, so desktop users had no way to navigate back from My Profile.
- **Cause:** Page relied solely on mobile header for back navigation.
- **Fix:** Added `<BackButton>` visible on `lg:` screens.
- **Fully closed:** Yes.
